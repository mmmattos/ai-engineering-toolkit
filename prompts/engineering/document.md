# Document

> Create clear technical documentation that explains software behavior, decisions, interfaces, and operational requirements.

# Purpose

Produce documentation that helps another engineer understand, use, operate, or change the system without requiring unnecessary context from the original author.

# Prompt

## Audience

Identify who will use the documentation and what they need to know.

## Content

Cover the relevant purpose, architecture, behavior, interfaces, configuration, dependencies, assumptions, and operational considerations.

## Examples

Use concise examples when they make the behavior or interface easier to understand.

## Accuracy

Base documentation on the actual code and configuration. Do not invent behavior that is not supported by the implementation.

## Maintenance

Prefer documentation that remains useful as implementation details evolve.

# Expected Output

## Overview

Provide a concise explanation of what the component does.

## Details

Document the important behavior, interfaces, dependencies, and operational considerations.

## Examples

Include practical examples where appropriate.

# Engineering Principles

- Document why, not only what.
- Keep documentation accurate and actionable.
- Prefer concise examples over excessive prose.
- Avoid documenting unsupported assumptions as facts.
